## 二、Experience 通道调研结论（任务就此关单）

HL-Mem 的 Experience 通道（158 行 service + 673 行 storage）是 Episode/Trace/Policy 三实体归纳层：Episode 记录任务经历（reward 回传 + outcome_summary），Policy 由 ≥2 次独立成功 Episode 支持（`min_support=2`，storage/experience.py:79-84）晋级 CANDIDATE→ACTIVE，3 次 failure（`retire_after_failures`）退役。

与本仓逐项对照后的映射结论：

| HL-Mem 实体 | 本仓等价物 | 缺口 |
|---|---|---|
| Episode（任务经历） | **task_id**（任务记忆的时间线就是 Episode 轨迹） | 无 |
| Trace（操作序列） | raw/ 捕获 + 任务记忆条目 | 无 |
| Policy（成功归纳） | **场景块（scenario）**——consolidate_notes 产出的就是可复用操作归纳 | 无 |
| Episode reward / outcome | — | **有，唯一真缺口** |

**裁决：不移植 Experience 通道**（不建 Episode 实体、不建 Policy 状态机）。理由：①前三个实体本仓已有等价物且形态更适合 Markdown+git 模型（HL-Mem 的表结构是 SQLite 自保手段，见「借鉴调研的排除判据」stable 笔记）；②Policy 晋级的「成功支持」判据要求归因「这次成功是因为用了这个 Policy」——归因过弱（成功原因多元），本仓 consolidate 的采纳信号（adopted）已是更诚实的代理；③唯一缺的 outcome 维度用 telemetry 方案补（成本约为移植的 1/10）。**「借鉴调研先证伪」又一实例：他仓的子系统拆开看，四分之三本仓已有。**

## 三、outcome 采集（唯一新建能力，约 1 人日）

### 事件形态（telemetry 第三事件类型）

```json
{"t": "outcome", "doc": "notes/xxx.md", "task_id": "他山之石",
 "at": "2026-09-14T11:30:00", "result": "success|failure",
 "note": "按这条笔记改了锁语义，测试全绿"}
```

- **双挂**（Q1=B）：doc + task_id。doc 是消费主体（哪个知识被用）；task_id 把 outcome 锚在任务经历上，天然形成「Episode → 用了哪些知识 → 结果如何」链（Experience 的精髓白拿）。task_id 尽力写：当前会话有绑定时从 session 取，否则可省。
- `result` 二值：success | failure。多档分级是伪精度——Agent 事后自评给不出可靠刻度。
- `note` 可选一句话上下文。**失败原因比失败本身值钱**（蒸馏反哺的原料）。
- 与 adopted 同为 plain append（低频事件，不做当日合并）；同 doc 同 task_id 的既有 adopted 事件存在时，report_outcome 顺手把 adopted 的 key 抄进事件，建立「引用→结果」关联。

### 采集入口：`report_outcome(doc, result, note?)`

- 唯一新工具，telemetry 薄壳（与 record_hit/record_adopted 同族，不碰 frontmatter——**不新增第 5 个 frontmatter 写入路径**，这是对 T5 原设计的关键偏离：T5 把 misrecall 写进笔记 metadata，需要锁与索引刷新；遥测路径零这些成本）。
- **采集时机**：Agent 在任务自然收尾时（测试跑完/验证通过/失败定位后）顺手报——它唯一能诚实判断成败的时点。不确认、不弹窗：采集是遥测不是落盘知识，天然免闸门（ADR-0002 同理）。
- registry 注册（handler + schema 两处）。

### 消费侧（全部 observe）

- `telemetry.aggregate_usage` 扩展：per-doc 的 `success/failure` 计数。
- `wiki_stats` 露出 `outcome` 段（success/failure/outcome_ratio），与 confidence_distribution 并排。

## 四、负例反哺（T8 保留，信号源改 outcome）

`distill_conversation(mode="prepare")` 与 `consolidate_notes(mode="prepare")` 响应增加 `negative_examples` 段：近期（默认 30 天）failure outcome 的 `{doc, note}` 列表（上限 5 条），提示语「以下知识近期被用错，提取/归纳新知识时规避同模式」。

- 纯提示，不改变任何提取/归纳行为（tri-state observe 形态）。
- **不做**检索侧反哺（query_wiki 结果加 failure 标注）——那是排序污染的温和版，数据未攒够前不动消费端（Q2=A）。
- 原 T8 的可选延伸（misrecall 自动生成 pitfall 笔记）**放弃**：outcome failure 的 note 已在蒸馏原料里， pitfall 化由蒸馏管线的既有确认闸门自然承接，不再单开通道。

## 五、消费预留：disputed_assets（T6 的 observe 化身，不实施）

**裁决：只报不降**（Q4=C）。原 T6 的自动降 shadow 放弃——一次任务失败可能是任务本身的问题而非知识错，小数据下自动降权误伤率高。

预留设计（数据攒够再议是否实施）：

- lint 新 check `disputed_assets`（warning）：failure ≥ 阈值（建议 2）且 success=0 且跨 ≥2 个任务（独立失败才算数——单任务连环失败只算一票）的资产清单。
- 若未来升 enforce：走批次一已铺好的 `confidence_level=shadow` 通道降权（`extra_meta` 一次写入），恢复走 confirm+evidence（复核即原谅）。
- 登记进 capability-matrix 时默认 `off`（check 未实施），实施时升 `observe`。

## 七、与既有决策的一致性核对

- tri-state 纪律（CONTRIBUTING.md）：采集=直接 `enforce`（遥测无副作用，与 hit/adopted 同权）；反哺=纯提示（observe 形态）；降权=未实施（off）。✓

- 「候选必有去向」：原 T5/T6/T8 各有归宿（§一表），无静默丢弃。✓
