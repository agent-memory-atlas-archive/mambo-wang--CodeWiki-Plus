## codewiki-plus 自动升级方案讨论
- 用户问：如何让用户无感知地自动升级 codewiki-plus。
- 现状：PyPI 发布（v5.13.1），入口 `codewiki` CLI + MCP server，无任何版本检查/自升级逻辑。
- 推荐方案：启动时后台静默升级（lazy self-update）——启动时查 PyPI JSON API（24h 缓存、fail-open、尊重 CODEWIKI_NO_AUTOUPDATE），发现新版后派生分离的后台子进程，等父进程退出后再 `sys.executable -m pip install -U`（Windows 文件锁：长驻 MCP server 加载 tree-sitter 原生依赖，运行中升级必失败）。
- 挂载点：`codewiki/cli/main.py:main()`、`codewiki/mcp/server.py:main()`、可选 SessionStart hook。
- 关键边界：必须用 `sys.executable -m pip`（全局 codewiki.exe 与 venv 错位是已踩过的坑，见 repowiki 笔记 2026-09-18）；源码安装（CODEWIKI_HOME/editable）跳过；只升不降。
- 配套：`codewiki upgrade` 显式子命令 + version 输出提示新版。
- 状态：方案已给出，待用户确认是否实现。
- 用户质疑：wait-for-exit 要等到智能体/IDE 关闭，等待过久。回应要点：
  - 运行中进程本就无法热加载，立即升级也不会让当前会话生效；且升级会造成懒加载版本混跑，"等退出"是正确性要求而非仅文件锁妥协。
  - 改进：①锁预检双模式（探测 .pyd 可写则立即升级，有锁才 wait-for-exit）；②CLI/hook 等短命进程触发点秒级落盘，互补；③等待设超时（30-60min）后重做锁预检；④lock file 防并发 pip。
  - 要求会话内生效的唯一路径：版本化安装 + shim（rustup 模式），但改变 pip 分发方式，暂不推荐。
