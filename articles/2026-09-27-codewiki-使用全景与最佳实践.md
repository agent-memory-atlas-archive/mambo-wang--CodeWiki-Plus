# CodeWiki-Plus 使用全景：一个仓库知识引擎的正确打开方式

> 写作时间：2026-09-27 · 基于 CodeWiki-Plus 当前 main 分支 README 与项目文档整理

**TL;DR:** CodeWiki-Plus 是一个由 AI IDE 自身模型驱动的仓库知识引擎，零 LLM API 配置，53 个细粒度 MCP 工具覆盖从文档生成到团队知识治理的完整链路。但工具多不等于都要用：正确的使用路径是分层的——先做一次性的安装接线，再按需初始化 Wiki 工作区，代码 Wiki 生成与增量更新跟着代码变更走，任务管理和团队记忆融合在长线工作中按需启用。本文给出这条路径的完整地图，以及每一步的判断标准。

---

## 一、先看全景：能力是分层的，不是一堆平铺的功能

把 53 个工具、23 个工作流 Prompt 直接甩给新用户，等于让人对着零件清单组装飞机。实际上这些能力有清晰的层次和启用顺序：

| 层 | 能力 | 核心工具/Prompt | 何时启用 | 频率 |
|---|------|----------------|---------|------|
| L0 | 安装与接线 | `pip install` + MCP 配置 + `install-hooks` | 只做一次 | 一次性 |
| L1 | 初始化 | `init-wiki` / `init-workspace` | 项目接入时 | 每项目一次 |
| L2 | 代码 Wiki 生成 | `generate-wiki` / `code-analysis` / `incremental-update` | 首次全量，之后随代码变更 | 按需 |
| L3 | 检索与沉淀 | `query_wiki` / `ingest_note` / `confirm_note` | 日常开发 | 每天 |
| L4 | 任务记忆 | `task-workflow`（10 个任务工具） | 长线任务跨会话时 | 按任务 |
| L5 | 团队记忆融合 | `capture_conversation` / `distill_conversation` | 团队协作、经验流失严重时 | 按团队节奏 |
| L6 | 知识治理 | `lint_wiki` / `consolidate_notes` / `skill_creator` / `report_outcome` | 知识库成型后 | 定期 |

一个关键认知：**L0-L2 解决「知识从代码里来」，L3-L6 解决「知识往代码里去」**。前者是引擎，后者是飞轮。只做前半段，你得到一份静态文档；跑通后半段，文档才会随团队经验持续演进。

## 二、L0：安装与接线，只做一次

三步，不需要任何 API Key：

```bash
# 1. 安装
pip install codewiki-plus
codewiki --version   # 验证

# 2. 配置 MCP Server（CodeBuddy 示例，Cursor/Claude Desktop 同理）
```

```json
{
  "mcpServers": {
    "codewiki": {
      "command": "codewiki",
      "args": ["mcp"],
      "maxOutputLength": 500000,
      "timeout": 36000000
    }
  }
}
```

配置完成后工具列表里应出现 53 个 `codewiki` 工具。

第 3 步容易被忽略但决定后面几层能不能转起来：

```bash
# 3. 接线团队记忆 Hook（检测到哪些 IDE 配置目录就为哪些接线）
codewiki install-hooks --repo-path <repo>
```

这一步拷贝 hook 脚本、合并 settings.json 注册、往 AGENTS.md 写入任务引导段。命令路径一律是项目相对形式，队友克隆到任意目录都能直接工作。支持 CodeBuddy、Qoder、Claude Code、TRAE（hook 档）和千问办公（prompt 档）。

**环境变量的坑：** `CODEWIKI_LANG`、`CODEWIKI_USER` 这类变量必须写在 MCP 配置 JSON 的 `env` 块里，写在 `.bashrc` 或系统环境变量里对 MCP 进程不可见——进程只在启动时读一次。真正需要用户设置的只有这两个，其余都有合理默认值，条件不满足不要动。

## 三、L1：初始化，每项目一次

初始化分单仓和多仓两种入口，选错入口后面每一步都会别扭。

**单仓用 `init-wiki`：** 创建 `repowiki/` 目录骨架和项目级 `schema.yaml`。这里有个最佳实践——生成后先编辑 `schema.yaml` 的 `purpose` 字段，用一两句话写清这个项目的定位。它是后续所有文档生成的「宪法」，Agent 写 overview、写模块文档时都会参考它。项目定位写得含糊，生成的文档就只会是正确的废话。

**多仓工作区用 `init-workspace`：** 首次初始化会先问你要知识布局（colocated 各仓自带 repowiki / centralized 集中存放），必须显式选择，不传参数工具会返回 `needs_layout_decision` 且不写任何产物。之后自动生成 bootstrap 克隆脚本、repo-map 导航骨架和工作区约定。重跑是零配置幂等的：痕迹齐备时只补克隆未克隆的业务仓，不碰其他文件。

判断标准很简单：你的团队是否在多个仓库间频繁跳转、需要跨服务调用分析？是，走 workspace；只是给单个项目建知识库，走 wiki。

## 四、L2：代码 Wiki 生成，跟着代码变更走

初始化完成后，在 Agent 模式输入一句话：

```
帮我分析当前仓库并生成 Wiki 文档，输出到 repowiki 目录。请使用中文撰写文档。
```

Agent 会走一条五阶段流水线：

```
阶段 1: analyze_repo → 组件索引、叶节点列表
        （自动检测 monorepo 子服务，构建跨服务调用关系）
阶段 2: get_prompt("cluster") → 聚类规则
        read_code_components → 自主推理分组为 3-8 个逻辑模块
        save_module_tree 保存
阶段 3: 按叶优先顺序逐模块生成文档
        叶模块：read_code → 推理 → write_doc_file
        父模块：读子文档 → 合成总览
阶段 4: 生成仓库总览 overview.md
阶段 5: close_session 释放资源，构建 BM25 索引
```

这条流水线背后有三个质量机制，值得知道但不需要手动干预：

1. **Evidence-Based 断言**——每条业务规则要求附代码证据（文件:行号 + 置信度），`lint_wiki` 的 `unsupported_claims` 检查会在超过 30% 断言无证据时报警，这是对 LLM 幻觉的硬约束。
2. **代码路由分类**——组件自动分为 business / boilerplate / infra 三类，DTO、Config 这类模板代码只注入签名不注入全文，典型 Java 仓库省 30% 以上 token。
3. **方法级增量检测**——再次调用 `analyze_repo` 时通过 `content_hash` 精确到方法级比对，只有真正变化的方法才标记 stale。

由此得出 L2 层最重要的最佳实践：**首次全量，之后永远增量**。代码有改动时说「帮我更新受影响的模块文档」，Agent 会走 `incremental-update` 流程只重生成受影响部分。全量重生成既浪费 token，又会覆盖掉你在文档上的手工修订。

另一个容易漏的细节：生成完务必让 Agent 走到 `close_session`。搜索索引在这一步才构建，跳过它，下一层的 `query_wiki` 就只能走降级路径。

## 五、L3：检索与沉淀，每天的日常

这一层是知识库的价值兑现处，两个动作：查（query_wiki）和写（ingest_note）。

**检索走渐进式阅读，不要一步到位：**

```
query_wiki(mode=overview)    → 初次接触项目，<500 token 了解全貌
query_wiki(mode=directory)   → 按类型分区定位目标模块/实体
query_wiki(query="xxx", hop=1) → 关键词检索 + 图谱关联扩展
query_wiki(mode=detail, page=...) → 深入阅读特定页面
```

从上往下逐层深入，每层都有 token 预算约束。直接跳到 detail 模式读全文，一个大点的仓库就能吃掉几万 token。检索结果带 `source_type` 标注（auto_generated / developer_note / ingested_source）和置信度，draft 笔记带 `[unconfirmed]` 前缀——消费前看一眼标注，这是知识可信度的第一道防线。

**沉淀走确认闸门，draft 不是终点：**

```
踩坑/决策发生
  → ingest_note(note_type="pitfall"|"decision"|..., status="draft")
  → 检索可见但标注 [unconfirmed]
  → confirm_note → 升级 stable，带证据（test_ref/commit_ref）可升 strong
  → reject_note → 降 shadow，默认不再被检索返回
```

8 种笔记类型对应不同场景：技术选型记 `decision`，踩坑记 `pitfall`，临时绕过记 `workaround`（要写恢复条件）。最佳实践是**让 Agent 在对话中主动提议归档，但确认权留在人手里**——LLM 自动沉淀的知识必须经研发确认，这是整个知识飞轮的信任基础。检索排序会叠加置信权重（strong +0.10 / shadow −0.30），确认得越充分，知识被复用的概率越高。

## 六、L4：任务记忆，长线任务才需要

任务记忆解决「长线工作跨会话断片」：一个任务持续数天、横跨多个会话，Agent 每次重启都从零开始。它与 Wiki 笔记的分工是——**Wiki 笔记沉淀跨任务的通用经验，任务记忆保存任务范围内的进度知识**（做了什么、下一步、待办）。

标准工作流：

```
会话开始：
  list_tasks(status="active") → 关联已有任务或新建
  → set_session_task 绑定会话
  → get_task_context 恢复上下文（描述 + 分层记忆 + 关联笔记）
  → pending_raw_count > 0：委托蒸馏 worker 后台补积压，不阻塞干活
  → compaction_due：顺手压缩旧记忆（原文进 archive，可找回）

会话过程中：
  关键进展 → add_task_memory 直写落盘（可逆操作免确认，ADR-0002）
  需要找回旧条目 → search_task_memories（条目级检索，archive 可搜）
```

三条硬约束记住即可：task_id 由标题生成且不可变，想改名只能删除重建；任务记忆直写免确认（有 archive 兜底，可逆），笔记必须走确认闸门（跨任务共享，不可逆）——两套闸门是刻意区分的；记忆超阈值（40 条 / 24KB）自动触发压缩，Agent 顺手完成，无需用户介入。

启用判断：如果你的任务当天能闭环，不需要这层；一旦工作以「周」为单位推进、且经常换会话甚至换人接手，任务记忆的投入产出比会非常高。

## 七、L5-L6：团队记忆融合与知识治理，知识库成型后再上

**L5 团队记忆融合**把「Agent 与研发的日常对话」变成可检索经验：

- `capture_conversation` 采集对话到 `repowiki/raw/`（仅落盘，永不自动蒸馏）
- `distill_conversation` 走 Mode C 协议：prepare 取 transcript → Agent 提取 → submit 入库（draft 待确认）

隐私语义要提前和团队对齐：检索命中与采纳记录会以 user_id 署名写入遥测并随仓库共享。不想用 git 真名署名的成员设 `CODEWIKI_USER` 花名，或在 `schema.yaml` 里关掉遥测退回纯本机模式。

**L6 知识治理**是知识库的体检和增值回路，四个动作各有节奏：

| 动作 | 工具 | 节奏 |
|------|------|------|
| 体检 | `lint_wiki`（25 项检查 + health_score） | 每周或大变更后 |
| 归纳 | `consolidate_notes`（笔记 → L2 场景块） | stable 笔记积累到一定量 |
| 编译 | `skill_creator`（确认知识 → SKILL.md 技能） | 反复出现的经验模式 |
| 反馈 | `report_outcome`（报告用了某文档后成败） | 每次任务收尾 |

`report_outcome` 值得单独说：它是 hit（看到）/ adopted（引用）之外的第三环信号，失败用例会自动进入蒸馏提示的 negative_examples，让「用错的知识」在新知识提取时被规避。知识库不只是越攒越多，还会越用越准。

`wiki_stats` 里的 strong 置信占比是北极星指标（目标 >60%），定期看一眼，低于阈值说明确认流程没跑起来，问题多半在流程不在工具。

## 八、最佳实践清单

把上面的内容压缩成一张可执行的清单：

**该做的：**

1. `install-hooks` 在仓库初始化时就跑，别等记忆积压了才补
2. `schema.yaml` 的 `purpose` 字段认真写，它是文档质量的杠杆点
3. 生成完确认 `close_session` 执行了，索引在这一步构建
4. 代码变更后走增量更新，永远不要习惯性全量重生成
5. 检索从 `mode=overview` 开始逐层深入，先看 est_tokens 再 expand
6. 笔记确认时尽量带证据（test_ref / commit_ref），strong 置信检索权重更高
7. 任务收尾时 `report_outcome`，让失败经验反哺蒸馏
8. 每周跑一次 `lint_wiki`，health_score 连续下降要查流程

**不该做的：**

1. 不要把环境变量写进 `.bashrc` 指望 MCP 进程读到，写 MCP 配置的 `env` 块
2. 不要跳过确认闸门直接引用 draft 笔记的结论
3. 不要在任务记忆和 Wiki 笔记里记同样的内容——通道互斥，各记各的
4. 不要关 `CODEWIKI_RAW_TOOL_DETAIL`（除非排障），关了之后技能编译缺素材
5. 不要给短期任务强上任务记忆，当天闭环的工作用不上这层

## 九、一个常见的落地误区

不少团队把 CodeWiki-Plus 当「文档生成器」用：装好、生成一次、把 repowiki 提交进仓库，结束。这样用，三个月后文档和代码一起腐烂，最后得出「AI 文档不靠谱」的结论。

问题不在生成质量，在于只跑了 L0-L2 就停了。这个系统的设计意图是：生成只是把代码里的显式知识搬进可检索的结构，而 L3-L6 才把对话里的隐性经验（为什么这么选、踩过什么坑、什么条件下绕过）持续注入同一个结构。增量更新让文档跟着代码走，确认闸门让经验可信，outcome 信号让错误知识被淘汰——飞轮转起来，知识库才会比任何一份手写文档活得更久。

接入成本其实很低：L0-L2 半小时，L3 是对话里顺口一句「记一下这个坑」，L4-L6 各自第一次用时照着 workflow prompt 走一遍就会了。从单仓 `init-wiki` 开始，用到哪层开哪层。
